# CryptoSense 風險彙整卡 — 設計（Spec，只寫 WHAT 與為什麼）

- **日期**：2026-08-15
- **階段**：P2 第一項
- **範圍**：個幣頁 AI 回答上方新增一張結構化的「風險彙整卡」
- **不在範圍**：K 線圖、技術指標、資料庫、對話持久化、回饋捕捉（P2 後續項目）

---

## 1. 目標

使用者在個幣頁問完一個問題後，除了現有的串流文字回答之外，**先看到一張結
構化的卡片**：風險定調、信心等級、正反觀點各 2–4 條、以及這個幣所屬生態的
資安事故紀錄。每一條觀點都能回溯到來源。

成功的定義不是「卡片畫出來了」，而是：

1. 卡片上的**每一個數字都可追溯到工具回傳**，模型沒有機會編造。
2. 產生失敗時使用者**看不到半殘的卡片**，而是照常拿到純文字回答。
3. 卡片底部的追問按鈕**讓使用者更容易問下一個問題**（產品北極星是追問率）。

## 2. 上下文：為什麼是現在

### 2.1 P1 現況（已實測確認）

- `components/Chat.tsx` 用 `useChat` 串流；每則 assistant 訊息渲染
  `TelemetryStrip`（工具呼叫徽章）→ `Markdown`（含 `[n]` 引用連結）→
  `SourceTray`（可展開的來源匣）。
- `lib/ai/sources.ts` 的 `createSourceRegistry()` 在**每一輪**建立，工具命中時
  `add()` 產生遞增的 `n`，三支工具共用同一套編號。
- `lib/ai/tools.ts` 三支工具：`getCoinData`、`getCryptoNews`、
  `searchKnowledgeBase`。
- 對話後會呼叫 `/api/suggestions` 產生正好 3 個追問按鈕，失敗時回退預設。
- 測試 87 個、24 個檔案全綠；`tsc --noEmit` 乾淨。

### 2.2 這次之所以可行的新條件

2026-08-14/15 新建立的風險語料（本機，尚未進向量庫）：

| 來源 | 份數 | 內容 |
|---|---|---|
| `rekt-corpus/` | 311 | rekt.news 逐案敘事報告，含協議、日期、損失金額 |
| `defillama-corpus/` | 623 | DefiLlama 事故資料，含攻擊手法分類、鏈、是否追回 |

- 兩者名稱可對上的僅 107 筆 → 合計約 **827 個不重複事故**。
- 對市值前 25 名幣種的覆蓋率：**23 / 25**（僅 INJ、TIA 無資料）。
- 金額單位已驗證為**美元**（Ronin 624,000,000／Poly Network 611,000,000／
  Phemex 85,000,000／Bybit 1,400,000,000 皆與公開紀錄一致）。

**這批語料是這張卡片的差異化來源。** 沒有它，卡片只是把行情和新聞重新排版；
有了它，卡片能講出「這條鏈上有 N 起有紀錄的事故，最大一起損失 X」——那是
競品卡片放不出來的內容。

### 2.3 套件現況（已驗證）

- `ai@7.0.4`。**`streamObject` 已被標記 `@deprecated`**，官方指示改用
  `streamText` 搭配 `output` 設定。
- 可用：`Output.object({ schema, name, description })`、
  `result.partialOutputStream`（`experimental_partialOutputStream` 已淘汰）、
  `NoObjectGeneratedError`。
- 實際執行模型由 `OPENAI_MODEL` 指定。

## 3. 產品行為（WHAT）

### 3.1 卡片出現的時機與位置

- **只在個幣頁**（`/coin/[id]`）的 AI 對話中出現。
- 每一則 **assistant 回答**上方一張卡，與該則回答綁定。
- 使用者送出下一個問題時，產生新的一張，舊的保留在對話歷史裡。

### 3.2 卡片內容

| 區塊 | 內容 | 由誰決定 |
|---|---|---|
| 風險定調 | 偏高風險／中性／偏低風險（三選一） | 模型 |
| 信心等級 | 高／中／低（三選一） | 模型 |
| 一句話結論 | 不超過 60 字 | 模型 |
| 正面觀點 | 2–4 條，每條可帶一個來源編號 | 模型 |
| 風險與盲點 | 2–4 條，每條可帶一個來源編號 | 模型 |
| **資安紀錄** | 事故次數、最大單筆損失、常見手法、最近一起 | **後端，模型碰不到** |
| 追問按鈕 | 正好 3 個 | 沿用現有 `/api/suggestions` |

### 3.3 使用者端可觀察的變化

- 個幣頁 AI 回答上方多一張卡片。
- 卡片以串流方式出現：**定調與信心先上色**，條列逐條長出來。
- 現有的串流文字回答、`TelemetryStrip`、`SourceTray`、追問按鈕**全部保留**，
  沒有任何既有功能被移除或改變。
- 市場總覽頁、個幣頁的行情與新聞區塊**完全不受影響**。

## 4. 架構決定與理由

### 4.1 兩段式，不是一次呼叫

**決定**：對話（第一段）與卡片（第二段）是兩次獨立的模型呼叫。第二段吃第一
段已經取得的工具回傳值，不重新呼叫工具。

**理由**：一次呼叫如果既要取資料又要排版，模型就有機會在排版時「順手」寫出
一個沒有出處的數字。分開之後，**卡片結構裡根本沒有欄位讓模型寫數字**——這是
結構上的不可能，不是靠提示詞叮嚀。

**代價**：多一次模型呼叫的延遲與成本。可接受，因為第二段的輸入是已經取得的
結構化資料，不需要再跑工具鏈。

### 4.2 模型只選項目與寫文字，數字一律由後端填

**決定**：schema 中所有會影響樣式的欄位一律是列舉（enum）；所有數值欄位不進
schema。

**理由**：
- 自由文字的風險等級會漂移成「較高風險」「風險偏高」「偏高」，前端的樣式
  判斷會全部掉到預設分支。
- 數值一旦讓模型輸出，就有幻覺空間，而這是一個講風險的產品——一個差了數量級
  的損失金額比不顯示更糟。

### 4.3 引用用編號，不用網址

**決定**：條列的來源以 `sourceId`（整數）表示，指向後端建立的來源清單；模型
不得輸出 URL。

**理由**：模型會編造網址。用編號的話，前端解析不到就退化成沒有連結的純文字，
天然擋掉捏造引用。這與 P1 既有的 `[n]` 引用機制是同一套編號。

### 4.4 欄位順序即顯示順序

**決定**：schema 的欄位宣告順序為：定調 → 信心 → 一句話結論 → 正面觀點 →
風險與盲點。

**理由**：結構化輸出是逐個鍵串流的。把定調放在最前面，卡片標題數百毫秒內就
能上色，而不是等整包 JSON 完成。這是使用者感知延遲的關鍵。

### 4.5 資安紀錄走預先計算的索引，不走語意檢索

**決定**：資安區塊的數字來自一份預先建好的索引檔，依鏈／協議查表，不經過
向量庫。

**理由**：
- 這一格要的是**確定的事實**（幾起、多少錢、什麼手法），不是語意相關的段落。
  語意檢索會給你「相關的三個片段」，但算不出「總共幾起」。
- 索引在建置期產生，執行期只是查表，沒有額外的 API 呼叫與延遲。
- 事故是歷史事件，不會變動，適合預先計算。

**代價**：新增事故要重新產生索引。可接受——這批資料的更新頻率以月計。

---

## 5. 防幻覺的三層機制

| 層 | 機制 | 擋掉什麼 |
|---|---|---|
| 1 | 數值欄位不進 schema | 模型編造價格、漲跌幅、損失金額 |
| 2 | 來源以編號表示，不接受 URL | 模型編造出處連結 |
| 3 | 樣式相關欄位一律列舉 | 分類漂移導致樣式失效、語意含糊 |

三層都是**結構性的**：不依賴提示詞被遵守。

---

## 6. 失敗模式與退路

| 失敗模式 | 症狀 | 處置 |
|---|---|---|
| 結構驗證失敗 | 模型輸出不符 schema | 不顯示卡片，照常顯示純文字回答；**絕不顯示半殘卡片** |
| 串流中途 | 條列文字邊打邊變、卡片高度跳動 | 一條觀點的必要欄位到齊才渲染；容器給最小高度 |
| 列舉值意外 | 收到未定義的定調字串 | 樣式判斷永遠有預設分支，不留白 |
| 來源編號不存在 | `sourceId` 指向不存在的來源 | 該條目不顯示連結，文字照常顯示 |
| 該幣無事故資料 | 索引查無此鏈／協議 | 資安區塊整塊不顯示，**不顯示「0 起事故」**（查無資料 ≠ 沒出過事） |
| 卡片 API 失敗 | 網路錯誤、逾時 | 靜默略過，不影響對話；不對使用者顯示技術錯誤 |

**最後一項的理由**：卡片是加分項，不是必要路徑。它壞掉不該讓對話跟著壞掉。

---

## 7. 不做什麼（YAGNI）

- **不**把卡片拆成正規化的資料表。這次沒有資料庫；未來要存就整張存成一個
  JSON 欄位。
- **不**新增獨立的情緒分析工具。新聞的判讀併入卡片生成即可。
- **不**在卡片裡放技術指標或 K 線——那是 P2 的下一項。
- **不**改動既有三支工具的介面。
- **不**改動 `/api/chat` 的既有行為。

- [ ] schema 的欄位宣告順序為：定調 → 信心 → 結論 → 正面 → 風險。
- [ ] 定調與信心為列舉型別。
- [ ] 正面與風險條列各限制 2–4 條。
- [ ] schema 中**沒有任何數值欄位**供模型填寫。
- [ ] 條列的來源為整數編號，schema 不接受 URL 型別。
- [ ] 使用 `streamText` + `Output.object`，**不使用已淘汰的 `streamObject`**。
- [ ] 卡片生成的輸入是既有的工具回傳值，不重新呼叫工具。

### API 層

## 9. 驗證方式

1. **單元測試**：索引查表（含查無資料）、schema 驗證（含超出列舉、條列超界）、
   來源編號解析（含指向不存在的編號）。
2. **元件測試**：串流中途只有部分欄位時的渲染、失敗時不顯示卡片、資安區塊
   在無資料時消失。
3. **回歸**：`npm test` 全綠 + `tsc --noEmit` 乾淨。
4. **金額正確性**：以第 8 節列出的四個已知事件對照索引輸出。

## 10. 待確認事項

- 卡片是否需要在**沒有任何工具被呼叫**的回答上出現（例如使用者問了範疇外的
  問題，AI 拒答）。**本設計的假設是：不出現**——沒有資料就沒有風險定調可言。
- 事故索引的更新節奏。本設計假設**手動重跑腳本**即可，不做自動排程。
